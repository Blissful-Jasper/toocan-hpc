# TOOCAN 并行架构设计与技术方案对比

> 约定：**[实测]** = 本项目在 Levante 上实际测得；**[推导]** = 由实测数据/源码分析推出；**[预期]** = 没有实测、仅为估计。
> 报告中没有把 [预期] 当作 [实测] 使用。性能表格见 `TOOCAN_performance_report.md`。

## 0. 结论先行

1. TOOCAN 的 DCS 识别 **不能** 拆成"先逐时刻独立识别、再做时间追踪"的两步法：它是 (t,y,x) 三维分割，时间连通性在
   区域生长与种子检测里就已经内置（见 `TOOCAN_algorithm_analysis.md` §4）。把它改成"逐帧 2D 识别 + 帧间对象匹配"是另一种算法，不是并行化。
2. 真正严格串行的只有一条链：**块 k → 块 k+1**（重叠区标签 + 全局标签计数器），全年约 400 个块。
   其余几乎都可并行：读取/OLR→BT 转换（逐时次）、阈值内的掩膜/冷体素表（逐体素）、掩膜输出（逐日）、FileTracking 统计（逐时次）、
   不同实验/不同数据集（完全独立）。
3. 在保持**逐位等价**的前提下，我们通过三类"工程等价"变换把这条串行链本身加速了 **61–98 倍**（单块 130 s → 2.1 s（16 线程）/ 1.3 s（64 线程）；单线程 7.3 s = 18 倍）[实测]，
   使得"一整年 = 一条 19 分钟的作业"（实测）。此时再为了"把链拆开"而引入近似（空间分块、时间分段），既没有必要，也有科学风险。
4. 推荐架构（方案 A′）：**C 核心 + OpenMP（单节点内）+ Python 做 I/O 流水线 + SLURM 作业数组做多节点**。
   MPI/Dask 只用于确实"令人尴尬地并行"的目录阶段，并且用 SLURM 数组即可，无需 MPI 通信。GPU 不推荐（第 6 节）。

## 1. 计算阶段与依赖图

```
            ┌──────────────────────────────────────────────────────────────┐
 IR(t)  ──► │ 读取 + OLR→BT（逐时次，独立）                                │──► BT 体 (T,Y,X)
            └──────────────────────────────────────────────────────────────┘
 BT体 + 重叠区标签 ─► [阈值循环 ×24:  SPREAD → LABEL_REGION → SPREAD] + 末次 SPREAD ─► 标签体 (T,Y,X)
                           ▲ 串行依赖：同一块内每步依赖上一步；块 k+1 依赖块 k 的最后 6 个时次
 标签体 ─► 写日文件（逐日，独立）          标签体+BT ─► 逐时次统计（独立）─► 按标签汇总 ─► INT/LC
```

| 阶段 | 并行性 | 约束 |
|---|---|---|
| 读取 / BT 转换 | 逐时次完全独立 | 受文件系统带宽限制 |
| 块内阈值循环 | 步间串行；**步内**可数据并行 | SPREAD 先到先得，见 §3 |
| 块间 | **严格串行** | 重叠区标签、`nb_ConvSeeds`、`labelMin` |
| 掩膜输出 | 逐日独立 | 压缩 CPU 开销 |
| 统计 → 目录 | 逐时次独立；聚合需全局 | 聚合是 O(观测数) 的轻量步骤 |
| 不同实验/年份 | 独立 | 跨年边界需上下文（§2.3） |

## 2. 拆分可行性分析（对应任务书第四节 1–6 条）

### 2.1 空间分块 —— 不严格等价，不推荐
* **可行性**：可以把域按经度分块并行（有 OpenMP/MPI 的能力），云团跨块时需要恢复连通性。
* **为什么不等价**：(a) SPREAD 是 FIFO 先到先得：一个体素若可被两个标签到达，归属取决于队列顺序；块边界处两侧各自的队列顺序与全局不同，
  竞争体素可能改判。(b) LABEL_REGION 是**单遍贪心扫描**，标签由扫描顺序产生；块内重新编号后，合并顺序、DFS 根的选择、
  `labelMCS_alreadyidentified`（"最后遇到的已固定 MCS"）都可能变化。(c) 孤立像元判据、域边界像元不参与检测，在人为边界处引入新的边界效应。
* **恢复跨块连通性的代价**：需要在每个阈值步（49 次 SPREAD/LABEL_REGION）做晕区（halo）交换和全局对象合并 —— 每块 2 个交换步 × 49 次，
  通信量与边界长度成正比；对 0.1°×0.1° 的 3600 经向点，块数 ≤ 数十时可行，但对象全局编号需要全局归约。
* **科学影响**：只在块边界附近出现；地球经向周期性（0–359.9°E）的接缝本来就被原始程序当作硬边界，因此全球 3600 点方向分块并不比原始更"坏"，
  但仍无法证明与原始等价。**本项目不做该近似**；有需要时作为可选方案，并必须用 `validation/compare_objects.py` 给出差异统计。

### 2.2 时间分块 —— 严格等价只能"串行链"，近似可行但有代价
* **块内**：不可拆（阈值循环 3D 连通）。
* **块间**：重叠区标签决定后续块，必须串行。**这是链，不是依赖可以消除的"弱依赖"。**
* **近似**：把时间轴切成若干段，每段前加 C 天上下文并独立运行，事后把相邻段的标签拼接（用户现有的 `run_monthly_segment.py` +
  `stitch_segment_tracks.py`）。每段从"空状态"启动，上下文区内的对象历史被截断，**长寿命 DCS 的出生时间与面积会不同**，
  标签在段间不一致，需按质心距离+共同时次事后匹配（阈值 50 km、≥2 时次）。
  这是近似；其科学影响由 `docs/TOOCAN_performance_report.md` 的"分段 vs 连续链"对比给出实测差异。
* **DCS ID/生命周期/追踪关系一致性**：连续链内全局唯一（`nb_ConvSeeds` 单调递增）；分段模式只能靠事后拼接。

### 2.3 多年份
* 不同**实验**（CNTL/P4K）、不同数据集：完全独立，任意节点。
* 同一实验的不同年份：**精确做法是一条跨年链**（状态 = 最后 6 个时次的标签 + 计数器，可检查点续跑；一年约 20–30 分钟，
  14 年 ≈ 5–7 小时 < 8 小时队列上限，且可用 `.state` 续跑）。若要并行年份，则每年一段并带上下文，属 §2.2 的近似。

### 2.4 "先并行识别每个时刻，再做时间追踪"是否等价？
**否。** 现有 FileTracking 阶段并不"追踪"——它读取 3D 分割已给出的标签，按标签聚合每时次统计；时间关联已在分割中完成。
若换成"逐帧 2D 连通域 + 帧间 IoU 匹配"，则合并/分裂定义、种子阈值层次（自上而下冷核优先）、`minLifetime` 的连续性判据都变了，是**新算法**。
本项目没有这样做。

## 3. 保持逐位等价的"工程等价"加速（核心成果）

下列变换都有简短证明，并经逐位对照验证（`TOOCAN_validation`，见性能报告 §验证）。

### 3.1 去掉每次调用 4.3 GB 的 Blob 初始化（Label_region）
原始 C 每次分配/初始化 `NBMAX_LABEL_OBJECTS=10⁶` 个 Blob（含 1000 整数的邻居表）。所有后续循环对未触及的条目都是空操作
（`label=0, flagRelabel=0`），因此改为惰性创建且遍历 `[0,最大下标]` 与原结果相同。[实测：占原单块时间的 28%（全域）～ 82%（小区域）]

### 3.2 SPREAD 只入队"前沿"体素
原始把所有已标记体素按光栅序入队再 FIFO。一个已标记体素若没有"可被占领的邻居"（未标记 ∧ 掩膜内 ∧ 温差条件成立），
处理它什么也不做；而标签只增不减、掩膜与温度静态，所以它之后也永远不会变成"可占领"。故只保留前沿体素（保持光栅序）与原队列在
所有产生副作用的元素上完全一致，**FIFO 次序与竞争体素归属不变**。

### 3.3 LABEL_REGION 只扫描"可能有副作用"的冷体素
调用开始时，体积中所有标签都属于**已固定 MCS**（flagFIX=1）——新生标签只在本次调用内临时存在。令 `U0` = 调用开始时"冷且未标记"的体素，
`V = {冷体素 v : OP(v) ∩ U0 ≠ ∅}`（OP = 11 点算子，对称）。若 `v ∉ V`，则 OP(v) 中所有冷体素都带着已固定标签：
不会有可赋值的邻居、不会产生新标签、记录的邻接关系只发生在已固定条目之间（它们的列表永不被读取）。所以扫描 `V` 与扫描所有冷体素结果相同。
累计面积/重编号循环只需处理本次调用中被赋过临时标签的体素（升序，以保持浮点截断累加顺序）。

### 3.4 确定性并行 BFS（层同步）
FIFO BFS 的次序 = (层数, 层内认领者位置, 邻居序号 k)。同一层内，一个体素被位置最靠前的合格认领者占领。把键 `key = 位置*10+k` 用原子 min
（CAS 写 `-key`）并行求解，下一层 = 赢家按 key 排序。边的合格性（掩膜、温差条件）是静态的，所以不同体素的认领互不影响；
结果与串行 FIFO 完全一致，**与线程数无关**（已用 1/4/7/16/24/32 线程在合成场与生产数据上验证）。

### 3.4' 其他与并行无关但必须保持的数值细节
* 量化 `(bt*100).astype(int16)`：Numba 对 float32 数组乘 Python 整数是 **float32** 乘法（`validation/test_quantization.py` 证明；
  用 float64 乘法会在 ≈1% 的 0.01 K 边界值上不同）。
* `int = int + float` 的逐次截断累加：按原顺序、原类型重现。
* `-ffp-contract=off`、不使用 `-ffast-math`。

## 4. 四种技术方案对比

| 维度 | A：C + OpenMP + MPI | B：Python+NumPy+Numba+Dask | C：Python + C 混合 + Dask/MPI | D：GPU（CuPy/CUDA） |
|---|---|---|---|---|
| 复用的核心 | 原 C 核心重构 | 重写为 Numba | **本项目采用的 C 核心** + Python 调度 | 重写为 CUDA |
| 逐位等价能力 | 高（已证明） | 中：Numba 与原实现用同一 JIT，可等价，但 `list` 动态数组与整数截断需小心；性能受限 | 高 | 低～中：原子操作次序不确定，需要确定性层同步 |
| 单节点性能 | 最佳（已实测，见性能报告） | Numba 版 SPREAD 即原始实现（≈36 s/块），扫描部分慢 | 同 A | 取决于数据驻留（见 §6） |
| 多节点 | MPI 对"链"无意义（无可并行的块），对目录阶段有意义 | Dask 调度开销 ≥ 数十 ms/任务，任务粒度应≥秒级 | SLURM 数组即可 | 同 A |
| 维护成本 | 中（C 核心+Python 驱动） | 低（纯 Python） | 中 | 高 |
| 风险 | 低 | 对象数不定、动态列表→JIT 编译慢，等价性难保证 | 低 | 高（算法本身不规则） |
| 推荐度 | ★★★ | ★ | ★★★★（本项目：A 与 C 的结合） | ★ |

**为什么不选 B：** 原始 SPREAD 已经是 Numba；真正的瓶颈在 LABEL_REGION 的内存初始化和全体积重复扫描，那是**算法结构**问题，不是语言问题。
Dask 对"一条 400 步的串行链"没有并行可挖，只会增加调度/序列化开销（每块 600 MB 数组往返）。

**为什么 MPI 在分割阶段不合适：** 没有可并行的块。若强行按空间分块，需要每个阈值步（每块 49 次）做晕区通信，并且不严格等价（§2.1）。
通信成本 ≈ 每次交换边界 2×(T×Y 或 T×X)×4 B；对 24 个阈值 ×2 次交换的总通信量不大，但**全局对象合并与确定性**才是难点。

## 5. 推荐架构与 SLURM 映射

```
┌── 作业 1：精确链（单节点，24–32 核）──────────────────────────────────────────────┐
│  读进程池(12) ─► 共享内存 BT ─► [C 核心 + OpenMP(24)] ─► 标签 ─► 写进程池(3) ─► 日文件 │
│  检查点：每块一个稀疏起始状态，作业被杀后从 ≤2 块之前续跑                          │
└────────────────────────────────────────────────────────────────────────────────────┘
        │ afterok
        ▼
┌── 作业 2：目录阶段，SLURM 数组（每月/每段一个任务，任意节点数）────────────────────┐
│  每任务：进程池按“日文件”并行 → 逐标签统计 → 压缩目录 + 兼容旧格式                    │
└────────────────────────────────────────────────────────────────────────────────────┘
```
* 多个实验、多个独立年块 = 多个"作业 1"并行（`submit_pipeline.sh`）。
* 目录阶段的"进程池"也可换成 `mpi4py` 多节点（`src/run_catalog_mpi.py`），但数组作业更简单、容错更好。

## 6. GPU 评估（[推导]，未实现）

* 数据体量：每块 BT 624 MB + 标签 624 MB；PCIe 4.0 单向约 25 GB/s → 一次上传/下载 ≈ 25–50 ms。
* 若只把 SPREAD 放到 GPU，每个阈值步需要把标签往返一次：49 步 × 2 × 0.6 GB ≈ 60 GB ≈ 3–5 s，**已超过本项目整块 CPU 耗时（≈2 s）**。
* 若整条阈值循环都放 GPU（避免往返），需要把 LABEL_REGION 的"单遍贪心扫描 + 邻接图 DFS 合并"改成等价的并行形式；其顺序语义
  （首次出现的邻居标签、DFS 最后遇到的固定 MCS）很难在 GPU 上逐位复现。
* BFS 按层推进，每层前沿很大时适合 GPU（[估计]：层数与前沿规模没有单独测量），但 CPU 线程版已把 SPREAD（前沿过滤+BFS）压到 0.7 s（64 线程）～1.4 s（8 线程）/块 [实测]，整块 1.3–2.1 s；其后的瓶颈是读盘与串行扫描，而不是 SPREAD。
* **结论**：在 I/O 成为瓶颈的当前状态下，GPU 的边际收益≈0，开发/验证成本很高。除非未来要处理 ≥0.04°、≥5 分钟的高分辨率数据，
  使 SPREAD 的前沿规模增大 10–50 倍，再重新评估（那时应整链驻留 GPU，并以确定性层同步重写 LABEL_REGION）。

## 7. 如何避免 Dask/MPI 的开销抵消收益

* 任务粒度：只对**≥10 秒**级、**数据已在本地**的任务做并行分发（月度目录任务 ≈ 分钟级；日文件统计 ≈ 秒级，用进程池而非调度器）。
* 不跨进程搬运大数组：读进程写入 `multiprocessing.shared_memory`，C 核心直接读；写进程从共享内存取日数据 —— **无 pickle、无拷贝**。
* 不在分割阶段使用调度器：链本身只有一条，`ProcessPool` + 双缓冲足以把读/写完全藏在计算后面（日志中 `io_wait≈0`）。
* 计算线程数 ≠ 进程数：OpenMP 线程数是 C 核心的参数；`OMP_NUM_THREADS=1` 用于 numpy/BLAS，避免超订。

## 8. 局限

* 若 `labels_present` 为空时（极端稀疏，重叠区无任何 DCS），原始程序保留旧簇表与旧 `labelMin`（该分支原本就可能越界）；
  本实现在同一情形下沿用"保留旧状态"的语义，但断点续跑无法精确还原该状态（会视为无已固定 MCS）。
* 当 `n−labelMin−1 ≥ nbMaxCluster` 时，原始程序越界写；本实现报错退出（宁可失败也不静默损坏）。
* 单节点内存：每块需要约 5–6 GB（BT/标签双缓冲 + 辅助结构）；更高分辨率网格需按比例增加。
